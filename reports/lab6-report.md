## 1. Introduction

The purpose of this laboratory was to evaluate the quality and maintainability of the Library Management API using software measurement and static-analysis tools.

Three tools were used: PMD, SpotBugs, and JaCoCo. They helped identify potential code-quality issues, analyze possible defects, and measure test coverage.

The laboratory also involved manually calculating cyclomatic complexity and coupling for the service classes, creating a Goal-Question-Metric (GQM) plan, and correcting one important static-analysis finding.

## 2. Static Analysis and Code Coverage

### 2.1 PMD Analysis

PMD was used to examine the source code and identify potential code-quality problems.

The analysis reported **9 findings**, all with priority level 3.

These findings mainly concerned coding practices and maintainability. They were reviewed rather than automatically treated as software defects.

### 2.2 SpotBugs Analysis

SpotBugs was used to identify potential programming errors and unsafe coding practices.

The initial analysis reported 11 findings. One important finding concerning the `ErrorResponseDTO` constructor was selected for correction.

After the correction and a new analysis, the total number of findings decreased from 11 to 10.

The selected constructor finding was eliminated successfully. Other findings were retained for review because some concerned framework-managed objects and shared references.

### 2.3 JaCoCo Code Coverage

JaCoCo was used to measure the percentage of executable source lines covered by the automated tests.

The overall line coverage was calculated before and after the quality improvement.

| Measurement | Before Improvement | After Improvement |
|---|---:|---:|
| Covered lines | 287 | 290 |
| Total executable lines | 303 | 306 |
| Overall line coverage | 94.72% | 94.77% |

The required minimum coverage was 40%, and the application exceeded this requirement in both measurements.

The class with the lowest coverage was `LibraryApiApplication`, with 33.33% coverage (1 out of 3 lines). The main method was not executed by the Spring application-context tests.

The service classes achieved strong coverage, with both `BorrowingService` and `ReservationService` reaching 100%.

Overall, the results show that the existing test suite exercises most of the application's executable code.

## 3. Cyclomatic Complexity Analysis

Cyclomatic Complexity measures the number of independent paths through a method. It was calculated manually using the formula:

**CC = Number of Decision Points + 1**

The analysis focused on the methods in `BorrowingService`.

| Method | Decision Points | CC | Risk Classification |
|---|---:|---:|---|
| Constructor | 0 | 1 | Simple |
| borrowBook() | 1 | 2 | Simple |
| returnBook() | 1 | 2 | Simple |
| applyReturnState() | 0 | 1 | Simple |
| getActiveBorrowings() | 1 | 2 | Simple |
| calculateFine() – public | 0 | 1 | Simple |
| calculateFine() – private | 1 | 2 | Simple |

The calculations follow the professor's classification from Chapter 6, page 60.

| Cyclomatic Complexity | Risk Classification |
|---|---|
| 1–10 | Simple program, no real risk |
| 11–20 | Moderately complex and risky program |
| 21–50 | Complex and highly risky program |
| Greater than 50 | Untestable and extremely risky program |

All analyzed methods have complexity values between 1 and 2. Therefore, they fall within the simple category.

This indicates that the methods have relatively straightforward control flow. However, low cyclomatic complexity does not guarantee the absence of defects.

## 4. Coupling and Instability Analysis

Coupling measures the dependencies between software components.

Two values were calculated:

- **Ce (Efferent Coupling):** Number of other classes a service depends on.
- **Ca (Afferent Coupling):** Number of classes that depend on the service.

Instability was calculated using:

**I = Ce / (Ce + Ca)**

The results were:

| Service Class | Ce | Ca | Instability |
|---|---:|---:|---:|
| BookService | 7 | 1 | 0.8750 |
| BorrowingService | 14 | 1 | 0.9333 |
| MemberService | 7 | 1 | 0.8750 |
| ReservationService | 12 | 1 | 0.9231 |

BorrowingService has the highest instability value, 0.9333. This is mainly because it depends on several entities, repositories, and supporting classes to manage borrowing operations.

A higher instability value indicates greater dependence on external components and potentially greater sensitivity to changes in those dependencies.

However, these values are based on the assignment's import-counting method. They should be interpreted as indicators rather than direct measurements of design quality.

## 6. Goal-Question-Metric (GQM) Plan

The GQM approach was used to connect the laboratory's quality objectives with measurable results.

### Goal

Evaluate the maintainability and regression reliability of the Library Management API through test coverage and static-analysis results.

### Question 1

Does the existing test suite provide sufficient code coverage to meet the required 40% overall line-coverage target?

**Metric:** Overall JaCoCo line coverage.

**Measurement:** Covered executable lines divided by total executable lines, multiplied by 100.

**Result:** Coverage increased from 94.72% to 94.77%, exceeding the required minimum.

### Question 2

Does correcting an important static-analysis finding remove the identified problem without breaking existing functionality?

**Metric:** Number of occurrences of the selected SpotBugs finding before and after correction.

**Measurement:** Compare the same SpotBugs rule and location before and after the change, then run the complete test suite.

**Result:** The selected `EI_EXPOSE_REP2` constructor finding decreased from one occurrence to zero. The total SpotBugs findings decreased from 11 to 10.

The complete GQM measurement plan is also documented in `docs/gqm.md`.

## 7. Quality Improvement

One important SpotBugs finding was identified in the constructor of `ErrorResponseDTO`.

The issue involved storing an externally supplied mutable map directly inside the object. Changes to the original map could therefore affect the contents of the error response.

To correct this issue, a defensive copy was introduced using `LinkedHashMap`, wrapped with `Collections.unmodifiableMap`.

This ensures that the DTO keeps its own snapshot of the supplied error details and prevents callers from modifying the stored map through the returned reference.

The results were:

| Measurement | Before | After |
|---|---:|---:|
| Selected constructor finding | 1 | 0 |
| Total SpotBugs findings | 11 | 10 |
| PMD findings | 9 | 9 |

Three focused regression tests were added to verify that:

- Changing the original input map does not change the stored error details.
- The returned map cannot be modified.
- Null field-error maps remain supported.

The original HTTP response behavior was also preserved.

## Conclusion

This laboratory demonstrated how software measurement tools can help evaluate the quality and maintainability of an application.

PMD and SpotBugs identified potential code-quality issues, while JaCoCo provided information about test coverage. Manual complexity and coupling calculations also helped evaluate the structure of the service classes.

The correction of the `ErrorResponseDTO` constructor demonstrated the importance of reviewing static-analysis findings and applying improvements without breaking existing functionality.

I learned that software quality cannot be evaluated using a single metric. Test coverage, complexity, coupling, static analysis, and code review provide different perspectives and should be considered together.

AI-generated code can accelerate development, but human review and verification remain necessary to ensure that the final application is reliable and maintainable.
